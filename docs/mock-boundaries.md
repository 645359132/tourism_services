# Mock and integration boundaries

This is the current integration truth table. The application has real client/server transport, authentication, persistence, transactions, REST endpoints, and WebSocket delivery, but every boundary below is either local, simulated, curated, or unconnected unless stated otherwise. UI phrases such as “真实 API” describe that implemented transport and persistence path; they do not mean a third-party provider, physical device, merchant, or public service is connected.

The public capability response exposes the principal modes as `ai=rules`, `crowd=simulated`, `gate=demo`, `map=schematic`, `merchant=demo`, `notification=in_process`, and `payment=demo`, all with `is_demo=true` ([capability registry](../server/app/api/routes/meta.py#L16)). Domain responses additionally carry `provider`, `mode` or `source`, and `is_demo` where relevant. Those fields and the explicit UI disclosure are part of the contract, not decorative debug metadata.

## Cross-cutting replacement rules

Any production adapter should meet these requirements before its `is_demo` flag changes:

1. **Preserve domain invariants.** Provider success does not bypass ownership, idempotency, state/version predicates, inventory conservation, schedule conflict checks, or points provenance.
2. **Represent uncertainty.** Timeout or lost response is not success. Persist provider correlation IDs and distinguish rejected, accepted, pending, and unknown outcomes where the external system supports them.
3. **Persist before fan-out.** REST and WebSocket clients recover from SQL. External callbacks and realtime events must update durable state idempotently before broadcasting.
4. **Keep disclosure granular.** Set `provider`, `mode/source`, and `is_demo` from the adapter that actually handled the operation. Mixed deployments may legitimately have live maps and demo payments, for example.
5. **Add operational contracts.** Real integrations require secret rotation, least-privilege credentials, request signing/callback verification, bounded timeouts, retry and circuit policy, audit/redaction, metrics, runbooks, and provider sandbox/production separation.
6. **Do not infer certification.** Passing application tests establishes repository behavior only. Security, privacy, accessibility, payment, life-safety, environmental, merchant, media-rights, and physical-access certifications require their own scoped evidence and review.
